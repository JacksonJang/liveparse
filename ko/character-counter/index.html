“한 글자”의 단위부터 확인

보이는 글자, 코드 포인트, 코드 유닛, 바이트는 서로 다릅니다

사람이 글자수를 셀 때는 화면에서 하나로 보이는 단위를 기대하는 경우가 많습니다. 이 페이지의 기본 글자수는 Unicode 확장 grapheme cluster입니다. 완성형 음절뿐 아니라 결합 자모와 여러 요소가 이어진 이모지를 사용자 인식 문자에 가까운 경계로 묶습니다. 다만 글꼴의 폭이나 특정 채용 사이트의 내부 규칙까지 재현하는 단위는 아닙니다.

코드 포인트는 U+D55C, U+1F600처럼 Unicode에 배정된 값입니다. JavaScript 문자열은 16비트 UTF-16 코드 유닛의 연속이며, U+FFFF를 넘는 코드 포인트는 2개 코드 유닛으로 표현됩니다. UTF-8 바이트 수는 같은 문자열을 UTF-8로 전송하거나 저장할 때 필요한 또 다른 길이입니다.

자소서 공고의 “1,000자”, 학교생활기록부 입력의 “바이트”, 서비스의 “한글 2자·영문 1자” 표시는 같은 계약이 아닙니다. 공백과 줄바꿈, 이모지, 결합 문자, 정규화, 인코딩의 규칙을 확인하고 최종 제출 화면의 값을 기준으로 판단해야 합니다.

공백 제외 값은 단순히 키보드의 스페이스만 지운 수가 아닙니다. Unicode White_Space에 해당하는 공백만으로 이루어진 grapheme을 제외하므로 일반 띄어쓰기, 줄바꿈, 탭과 그 밖의 Unicode 공백이 빠집니다. 기본 글자수와 1,000자 목표 게이지는 공백을 포함합니다.

어떤 사이트는 줄바꿈을 빼고, 어떤 사이트는 공백을 포함하며, 또 다른 사이트는 서버에서 정규화한 뒤 자체 규칙을 적용할 수 있습니다. 이 페이지의 숫자는 기준을 비교하고 초안을 조정하는 도구이며, 특정 채용 사이트나 공공 입력 폼과의 완전한 일치를 주장하지 않습니다.

한글은 보이는 음절과 저장 형태가 다를 수 있음

완성형 한과 분해된 자모 한은 모두 하나의 grapheme으로 보일 수 있지만 내부 코드는 다릅니다. 이 페이지는 NFC, NFD, NFKC, NFKD 정규화를 적용하지 않으므로 코드 포인트, UTF-16, UTF-8, 정책 가중치의 차이를 그대로 보여 줍니다. 서명, 해시, 데이터베이스 키, 입력 제한에 정규화 규칙이 있다면 그 계약을 별도로 따라야 합니다.

“한글 2, 영문 1”을 정확히 이름 붙이기

ASCII 1·비ASCII 2는 인코딩이 아니라 플랫폼 정책 가중치입니다

한국어 화면의 정책 가중치는 현재 문자열을 코드 포인트 단위로 순회합니다. U+0000부터 U+007F까지의 ASCII 코드 포인트에는 1을, 그 밖의 모든 코드 포인트에는 2를 더합니다. ASCII 스페이스와 줄바꿈도 각각 1이며, 한글 음절, 자모, 비ASCII 공백, 이모지 등은 코드 포인트마다 2입니다.

이 숫자를 UTF-8 바이트, UTF-16 바이트, EUC-KR 또는 CP949 바이트라고 부르면 안 됩니다. 예를 들어 한은 UTF-8에서 3바이트지만 이 가중치에서는 2이고, 😀은 UTF-8에서 4바이트지만 이 가중치에서는 2입니다. 분해된 자모는 코드 포인트가 3개라 가중치 6이 됩니다.

일부 레거시 입력 폼이 비슷한 규칙을 사용할 수 있지만, 이름이 같아 보여도 세부 구현은 다를 수 있습니다. 서비스가 “바이트”라고 표시하더라도 실제 규칙을 문서로 확인하고, 최종 폼의 수치와 대표 문자를 직접 대조하세요.

UTF-8은 별도 지표

실제 UTF-8 저장·전송 크기가 필요하면 “UTF-8 바이트” 값을 사용하세요. 단독 surrogate가 있으면 조용히 대체하지 않고 결과를 이용 불가로 표시합니다.

로컬 계산과 엄격한 인코딩

UTF-16, UTF-8, textarea 개행 변환의 경계를 알기

UTF-16 코드 유닛은 JavaScript 문자열의 길이입니다. 대부분의 완성형 한글 음절과 자모는 각각 1코드 유닛이지만 많은 이모지는 2코드 유닛의 surrogate pair를 사용합니다. UTF-8 바이트는 현재 DOM 문자열을 엄격한 UTF-8로 인코딩했을 때의 길이입니다.

JavaScript 문자열에는 드물게 짝이 없는 surrogate 코드 유닛이 들어갈 수 있습니다. 이는 Unicode scalar value가 아니므로 이 페이지는 U+FFFD 대체 문자의 3바이트를 원문 바이트인 것처럼 표시하지 않습니다. 대신 엄격한 UTF-8 수치를 이용 불가로 표시하고 문제 위치를 알려 줍니다.

HTML textarea는 CRLF와 CR 줄바꿈을 JavaScript가 읽기 전에 LF로 변환합니다. 따라서 Windows 원본 파일의 개행 바이트를 그대로 재는 도구가 아닙니다. 원본 파일 전체의 바이트, BOM, 다른 인코딩이 계약의 일부라면 해당 파일을 직접 검사하는 별도 도구가 필요합니다.

브라우저 안에서만 글자수 계산

자소서를 계산 서버로 보내지 않고 분량 확인

계산은 전용 Web Worker를 사용해 현재 브라우저 탭에서 실행됩니다. LiveParse는 입력한 글을 글자수 계산용 API로 의도적으로 전송하거나 서버 측 기록으로 저장하지 않으며, 클립보드를 자동으로 읽지 않습니다. 한 번의 입력은 최대 200,000 UTF-16 코드 유닛입니다.

브라우저 로컬 처리가 기기 전체의 격리를 뜻하지는 않습니다. 브라우저 확장 프로그램, 클립보드 관리 앱, 화면 공유, 접근성 소프트웨어, 운영체제 기능은 이 페이지의 통제 밖입니다. 주민등록번호, 연락처, 회사 기밀처럼 분량 확인에 필요 없는 정보는 제거하고 사용하는 기기의 보안 정책을 따르세요.

페이지 자체를 불러오려면 네트워크 요청이 필요하지만, 입력 내용은 계산 요청 URL이나 로컬 저장소에 넣지 않습니다. 브라우저를 닫거나 페이지를 새로 고치기 전에 필요한 원문을 사용자가 직접 보관해야 합니다.

글자수 세기 FAQ

이 도구에서 한 글자는 무엇을 뜻하나요?

기본 글자수는 사용자가 한 글자로 인식하는 단위에 가까운 확장 grapheme cluster 수입니다. 코드 포인트, JavaScript의 UTF-16 코드 유닛, UTF-8 바이트도 따로 보여 주므로 제출 사이트가 지정한 단위와 비교할 수 있습니다.

공백 제외 글자수에서는 무엇이 빠지나요?

Unicode White_Space 속성에 해당하는 공백만으로 이루어진 grapheme을 제외합니다. 일반 띄어쓰기뿐 아니라 탭과 줄바꿈 등도 빠집니다. 기본 글자수와 1,000자 목표는 공백을 포함한 grapheme 수를 사용합니다.

완성형 한글과 분해된 자모는 왜 수치가 다른가요?

완성형 ‘한’과 초성·중성·종성 자모로 이루어진 ‘한’은 모두 한 grapheme으로 묶일 수 있지만, 전자는 코드 포인트 1개이고 후자는 3개입니다. 정규화하지 않으므로 UTF-16, UTF-8, 정책 가중치의 차이가 그대로 남습니다.

ASCII 1·비ASCII 2 가중치는 바이트 수인가요?

아닙니다. 현재 문자열을 코드 포인트로 순회해 U+0000–U+007F은 1, 그 밖의 모든 코드 포인트는 2로 더하는 별도 플랫폼 정책입니다. UTF-8, UTF-16, EUC-KR, CP949의 실제 인코딩 바이트 수와 같다고 해석하면 안 됩니다.

자소서 1,000자 제한과 정확히 같나요?

기본 목표는 공백을 포함한 grapheme 1,000개를 기준으로 남은 수와 초과분을 보여 줍니다. 채용 사이트마다 공백, 줄바꿈, 이모지, 바이트 또는 자체 가중치 규칙이 다를 수 있으므로 최종 제출 폼의 표시값과 공고 기준을 우선해야 합니다.

입력한 자소서가 전송·저장·정규화되나요?

계산은 현재 브라우저 탭에서 실행되며 입력을 글자수 계산용 API로 의도적으로 전송하거나 서버 기록으로 저장하지 않습니다. Unicode 정규화는 하지 않지만 HTML textarea는 CRLF와 CR 줄바꿈을 분석 전에 LF로 바꿉니다.
